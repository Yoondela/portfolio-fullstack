# Portfolio v1 Requirements

## 1. Purpose

Engineer Portfolio is a personal software engineering portfolio and small content-management application.

The public application showcases the developer's projects, technical knowledge, and engineering thinking.

The application itself is also a demonstration of software engineering practices including Next.js, TypeScript, PostgreSQL, authentication, authorization, validation, CRUD, testing, CI/CD, and deployment.

## 2. Actors

### Visitor

An unauthenticated person viewing the portfolio.

### Administrator

The portfolio owner who is authenticated and authorized to manage projects.

## 3. Public functionality

### Home

Route: `/`

Visitors can view published projects.

Each project contains:

* name
* description
* technologies
* optional website URL
* optional GitHub URL
* features
* optional plain-text note (maximum 400 characters)

Each feature contains:

* name
* description
* screenshots

### Engineering

Route: `/engineering`

Visitors can read the engineering notebook.

Initial topics may include:

* architecture
* database decisions
* authentication
* testing
* security
* DevOps
* engineering lessons

Engineering content is initially static.

### Contact

Route: `/contact`

Visitors can view contact information and submit a contact form.

The contact form sends a required sender email address, subject, and message
directly to Formspree.
The application does not persist contact messages in PostgreSQL.

## 4. Administrative functionality

### Manage

Route: `/manage`

Only the authorized administrator may access project management.

The administrator can:

* view projects
* create projects
* edit projects
* delete projects
* add, edit, or clear an optional project note

### Features

The administrator can:

* add features
* edit features
* remove features

### Screenshots

The administrator can associate screenshots with features.

Screenshot files are stored in Supabase Storage. PostgreSQL stores the
provider-independent object path, while pre-existing external URLs remain in a
temporary nullable compatibility field until they are migrated or removed.

## 5. Routing

The initial route structure is:

```text
/
├── /engineering
├── /contact
└── /manage
    ├── /projects
    ├── /projects/new
    └── /projects/[id]
```

This intentionally demonstrates:

* static routes
* nested routes
* dynamic routes
* protected routes

## 6. Project requirements

Projects support:

* explicit display ordering
* published/unpublished state
* creation timestamp
* update timestamp

Only published projects appear on the public homepage.

## 7. Non-functional requirements

### Type safety

Use TypeScript throughout the application.

Do not use `any`.

### Security

Administrative operations require authentication and server-side authorization.

Secrets must not be committed or exposed to the client.

User-controlled input must be validated.

### Accessibility

Use semantic HTML and accessible forms and interactions.

### Maintainability

Prefer simple, understandable code and clear responsibilities.

Avoid unnecessary abstractions and dependencies.

### Performance

Use appropriate Next.js server-side capabilities and avoid premature optimization.

### Deployment

The application must eventually be deployable to production.

### Quality

The project should eventually have automated:

* linting
* type checking
* tests
* production builds

## 8. Out of scope for v1

The following are intentionally excluded:

* public user accounts
* multiple administrator roles
* social features
* comments
* likes
* collaboration
* full CMS functionality
* messaging
* notifications
* analytics platform
* search engine
* microservices
* GraphQL
* real-time functionality
* mobile application
* AI features
* payments

Additional functionality must have a clear requirement before being added.
